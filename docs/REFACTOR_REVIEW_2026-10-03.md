작성일: 2026-10-03, 한국 시간. 작업 원본: `C:/Users/JUNGLE/Documents/GitHub/wavcloud`.
기존에 수정 중이던 파일을 유지하면서 이번 변경을 추가했다.

## 현재 구조

```mermaid
flowchart LR
  A[Android WebView · 내장 app.html] -->|명령·상태| B[NativePlayerBridge · Media3 PlaybackService]
  A --> C[API client]
  A --> D[NativeOfflineBridge · 앱 내부 음원]
  A --> E[ArtworkResolverBridge · 앨범아트]
  F[웹 브라우저 · PWA] --> G[Nginx · HTTPS]
  C --> G
  B -->|스트리밍| G
  G --> H[Fastify API · 인증·음원 목록·업로드]
  H --> I[메타데이터 스캔 · 사용자별 LibraryStore]
  H -->|X-Accel-Redirect| G
  G --> J[/mnt/music · 음원 파일]
```

| 영역 | 실제 경로와 역할 |
| --- | --- |
| 운영 서버 | Ubuntu, Node.js 20.20.2, systemd `cloudmusic.service` |
| API | `/opt/cloudmusic/server/dist`, Fastify, 포트 3000 |
| 웹 화면 | `/opt/cloudmusic/client/dist`, 현재 `assets/index-v23.js` / `index-v23.css` |
| 프록시 | `/etc/nginx/sites-available/cloudmusic`, HTTPS와 내부 음원 전달 |
| 음악 | `MUSIC_DIR=/mnt/music`, 사용자별 디렉터리, 일부 실제 저장 경로는 `/mnt/data` |
| Android 화면 | `android-app/web-src` → `tools/sync-web.mjs` → 내장 `app.html` |
| Android 재생 | `PlaybackService`, `NativePlayerBridge`, `PlayerStateDispatcher` |
| 다운로드 | `OfflineAudioStore`에 저장하고 Media3가 로컬 URI로 재생 |
| Android 파일 선택 | 새 `FileChooserBridge`가 HTML 파일 입력을 시스템 파일 선택기에 연결 |

서버에는 원본 TypeScript와 웹 개발 프로젝트가 없으며 실행용 JavaScript 번들이 남아 있다.
로컬 `server/dist`와 작업 시작 시 운영 파일의 해시가 모두 일치했다.
Android의 내장 UI와 운영 PWA는 별도의 배포물이다. 이번 UI 변경은 새 Android APK에 포함된다.

## 수정 사항

| 문제 | 수정 및 근거 |
| --- | --- |
| 검색이 열리지 않음 | CSS가 검색 버튼과 입력을 항상 숨기던 규칙 제거. 입력은 헤더 아래 한 줄로 표시. 일본어 검색과 결과 없음 화면을 브라우저에서 확인. |
| 빈 라이브러리에서 무한 로딩 표시 | 서버 목록을 성공적으로 받은 상태를 별도로 기록. 빈 목록에는 곡 없음 안내와 업로드 버튼 표시. |
| 검색·저장됨 목록의 메뉴가 다음 줄로 밀림 | 곡 목록의 공통 행 스타일을 재사용하여 제목·길이·곡 메뉴를 한 줄에 배치. |
| 필터된 곡을 정렬하면 전체 목록이나 재생목록에서 숨겨진 곡이 빠질 수 있음 | 검색 중과 저장됨 탭에서는 정렬을 막고 드래그를 비활성화. 전체 목록에서만 순서 변경을 수행. |
| 오프라인 조회가 늦게 끝나 다른 탭을 덮어쓸 수 있음 | 화면 렌더링 버전을 확인하고 이전 조회 결과는 반영하지 않음. 늦은 조회 완료를 회귀 검사에 추가. |
| 재생목록 JSON 손상으로 앱 초기화 실패 | JSON 타입과 각 항목의 이름·곡 목록을 검사. 유효한 항목을 복구하고 원래 저장값은 불러오기 단계에서 유지. |
| 저장 공간이 부족하면 받은 곡 목록도 표시되지 않음 | 선택적인 곡 캐시 저장 실패와 화면 표시를 분리. 네트워크로 받은 목록은 계속 사용. |
| 중복 탭으로 요청·저장 작업 반복 | 곡 목록 요청을 공유하고 같은 곡의 오프라인 저장 작업을 한 번만 수행. 실패 후 버튼과 안내 복구. |
| URL의 로그인 토큰이 초기 API 객체에 반영되지 않음 | URL 토큰을 저장할 때 API 객체에도 함께 반영. |
| Android 업로드에서 파일 선택이 연결되지 않음 | 기본 WebChromeClient에 없던 파일 선택 콜백 구현. 선택 취소, 새 요청, 종료 시 대기 콜백 정리. APK 컴파일 확인; 휴대폰 실행은 미검증. |
| 스캔 중 업로드한 곡이 스캔 결과에 덮여 사라질 수 있음 | 사용자별 LibraryStore로 목록·ID 조회를 통합. 스캔 도중 업로드된 항목은 최종 목록에 병합. 실패한 스캔은 이전 목록 보존. |
| 로그인 요청의 username이 숫자면 500 오류 | 입력 타입·길이 검증. 운영 서버에서 500을 재현하고 반영 후 400으로 변경된 것을 확인. |
| 잘못된 폴더·파일 업로드 입력 | 폴더명 검증, 지원 확장자 제한, 빈 파일 400, 크기 초과 413, 미지원 형식 415, 파일 충돌 409. |
| 업로드 실패 응답 직후 임시 파일이 남아 보일 수 있음 | 임시 파일 정리가 완료된 뒤 실패 응답을 반환. 통합 검사에서 발견하고 수정. |
| 직접 스트리밍에서 suffix·역방향·잘못된 Range 처리 | Range 파서를 분리하고 suffix, 열린 끝, 범위 끝 자르기, 416 처리 구현. Fastify가 스트림과 연결 종료·오류를 관리하도록 변경. |

## 유지보수 경계

- `web-src/scripts/api-client.js`: 인증, API 요청, 응답 검증, 요청 제한 시간, 미디어 URL, 업로드 통신.
- `web-src/scripts/library-data.js`: 저장 데이터 검증, 목록 불러오기, 재시도, 중복 요청, 오프라인 작업 복구.
- `web-src/scripts/library-view.js`: 앨범·폴더·검색·저장됨 화면과 행 배치, 화면 전환 시 조회 결과 취소.
- `app/src/main/java/.../FileChooserBridge.kt`: Android 파일 선택 수명.
- `server/dist/services/library-store.js`: 사용자별 목록과 스캔·업로드 병합.
- `server/dist/utils/byte-range.js`, `request-validation.js`: HTTP 입력 규칙.

생성된 `app.html`을 직접 편집하지 않는다. 앱 화면을 바꾼 뒤 빌드 스크립트로 다시 생성한다.
API와 사용자 입력 규칙을 고칠 때 압축된 런타임에 새 패치를 겹치지 않고 위 책임 파일에서 변경한다.

## 다음 리팩토링 우선순위

1. 서버 TypeScript·웹 개발 원본 복구와 공통 모델 정의. 현재 서버 실행용 JS와 Android의 압축 런타임을 직접 유지하는 비용이 크다. 플레이어·업로드·저장소를 읽기 쉬운 모듈로 순서대로 옮긴다.
2. 서버 시작 시 전체 음악 스캔을 기다리는 구조 개선. 검증된 목록을 디스크에 저장해 복원하고 변경된 파일만 검사하면 재시작 동안 API가 오래 열리지 않는 문제를 줄일 수 있다. 음악 마운트가 정상인지 확인하는 상태 API도 함께 설계한다.
3. 계정별 로컬 데이터 분리. 현재 재생목록과 곡 캐시의 브라우저 저장 키는 계정 구분이 없어 계정 전환·재설치 정책을 명확히 해야 한다.
4. 인증·네트워크 설정 정리. 현재 토큰 만료가 3,650일이고, 미디어 URL의 토큰이 요청 로그에 남을 수 있다. 토큰 만료·갱신 방식과 로그 마스킹을 함께 변경해야 한다. API는 0.0.0.0:3000에서 수신하고 UFW는 비활성 상태이므로 클라우드 방화벽 규칙을 확인한 뒤 내부 바인딩 범위를 정한다.
5. 업로드의 새 폴더 입력도 앱 내부 창으로 통일하고 음원 내용 검증·취소·일부 실패 재시도까지 분리한다. 이번에는 파일 선택 연결과 서버의 잘못된 입력 처리부터 수정했다.
