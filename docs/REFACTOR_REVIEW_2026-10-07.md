# WavCloud 추가 리팩토링 결과

작성일: 2026-10-07, 한국 시간. Android 버전: 0.1.33 / 코드 34.
원격 `main`과 로컬 코드는 작업 시작 시 동일했으며 미커밋 변경은 없었다.

## 이번 변경

압축된 `runtime.js`에서 브라우저 오프라인 저장 클래스 약 3,400자를 제거하고
`web-src/scripts/offline-store.js`로 분리했다. 화면과 플레이어는 기존 `A` 객체의 계약을 계속 사용한다.
Android 연결은 `native-offline.js`가 같은 객체의 메서드를 제공한다.
이제 오프라인 저장의 규칙을 압축 코드에 패치를 추가하지 않고 읽기 쉬운 파일에서 수정한다.

| 확인된 문제 | 변경 |
| --- | --- |
| 같은 곡의 자동·수동 저장이 겹치면 중복 요청 가능 | 곡별 전송 작업을 공유. 중복 수동 저장과 네이티브 다운로드도 하나의 작업을 기다림. |
| JSON 문법은 맞지만 저장 ID 값이 배열이 아닌 경우 동작 실패 | 배열·문자열 ID를 검사하고 중복 제거. 기존 JSON을 읽는 단계에서 원본을 덮어쓰지 않음. |
| 부분 응답·빈 파일·오류 페이지를 정상 음원으로 저장 가능 | 200 응답, 음원 MIME, 크기와 본문 검증 후 캐시에 게시. 저장 실패를 성공 이벤트로 알리지 않음. |
| 멈춘 브라우저 다운로드가 끝없이 대기 | 전송과 본문 읽기를 포함한 15분 제한 시간. 실패 시 요청 기록 정리로 재시도 가능. |
| 수동 저장이 자동 캐시 한도를 차지해 자동 저장이 바로 지워짐 | 자동 저장 40곡 한도는 수동 저장과 진행 중 수동 요청을 제외해 계산. |
| 브라우저 삭제 오류를 삼켜 성공 안내가 표시됨 | 오류를 호출자에게 전달. 실제 삭제 완료 후에만 완료 이벤트 발생. |
| 여러 곡의 Android 캐시 이전이 하나의 네이티브 가져오기 스트림에서 충돌 | 같은 곡의 이전 요청을 공유하고 서로 다른 곡은 직렬 처리. |
| 실패한 캐시 이전을 영구적으로 시도 완료로 기록 | 작업 종료 시 진행 기록 제거. 실패한 음원 원본은 유지하여 다음 조회에서 재시도. |
| 다운로드 도중 삭제하면 나중 완료된 파일이 다시 나타남 | 진행 중인 다운로드·이전을 기다린 다음 파일 삭제. 아직 이전하지 않은 브라우저 원본도 삭제. |
| 잘못된 네이티브 콜백이 예외 또는 잘못된 성공을 유발 | JSON과 결과 타입 검사. 알려진 요청의 잘못된 결과는 실패로 처리하고 재시도 가능. |
| 검색·재생목록·저장됨 화면의 저장 표시 갱신 누락 | 모든 라이브러리 곡 행에 저장 표시를 만들고 관련 이벤트에서 함께 갱신. |
| 127.0.0.1에서 연 개발 화면이 localhost API를 호출 | 개발 화면의 호스트명을 API 주소에 사용. localhost와 127.0.0.1 각각 검사. |

## 검증

- JavaScript 검사 스크립트 12개 통과. 기존 재생·대기열·앨범아트·저장 데이터 검사 포함.
- 새 `test-offline-store.cjs`: 공유 전송, 부분 응답·빈 파일·잘못된 MIME·길이 불일치,
  실패 후 재시도, 수동 저장 보존, 삭제 실패, 멈춘 요청, 같은 곡과 다른 곡의 병렬 이전,
  이전 실패 후 재시도, 다운로드 중 삭제, 잘못된 콜백과 이전 전 원본 삭제를 검사.
- Android `testDebugUnitTest assembleDebug`와 APK 패키징 성공.
- 390×844 브라우저 화면에서 일본어 검색 → 저장 → 저장됨 목록 → 삭제 → 빈 목록 → 다시 저장 → 재생 상태 확인.
  검색 결과의 `data-offline-saved=true`와 표시 배지 `hidden=false`를 실제 DOM에서 확인.
- UI 검증은 로컬 테스트 API와 무음 WAV를 사용했다. 네이티브 이전·다운로드 동시 작업은 브리지 모의 검사로 검증했다.
  실제 휴대폰 설치와 네트워크 단절·잠금 화면·백그라운드 재생은 실행하지 않았다.

## 남은 개선 우선순위

1. **서버 시작과 메타데이터 캐시**: 현재 코드가 전체 스캔을 기다린 뒤 API를 열므로 재시작이 느리다.
   목록 스냅샷, 파일 변경 여부 검사, 시작 상태 표시를 함께 설계한다.
   시작 스캔과 사용자가 요청하는 스캔·업로드가 같은 작업 관리자를 사용하도록 통합해야 한다.
2. **계정별 데이터 수명**: 재생목록·곡 캐시·곡 순서·네이티브 재생 대기열을 계정 전환 정책과 함께 분리한다.
   기존 계정 구분이 없는 데이터의 소유자를 결정할 이전 절차가 필요하다.
3. **플레이어·업로드 코드 분리**: 압축된 브라우저 플레이어와 라이브러리 클래스가 남아 있다.
   재생 복구와 대기열 계약을 보존하는 단위로 옮기고, 새 폴더 입력도 앱 내부 창으로 통일한다.
4. **인증·운영 설정**: 토큰 만료·갱신, 미디어 URL의 토큰 로그 처리, 실제 클라우드 방화벽 범위를 확인한다.
   기존 사용자가 재생 중에 끊기지 않도록 갱신 계약과 적용 절차를 마련한다.

새 기능은 재생목록 서버 동기화, 앨범 일괄 저장·진행률·취소, 취침 타이머 순으로 제안한다.
특히 일괄 저장은 이번에 분리한 저장 모듈에 작업 목록을 추가하는 방식으로 구현할 수 있다.
